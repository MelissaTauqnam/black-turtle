      Les bases de n8n
      
Un workflow = un déclencheur, des nœuds, et des données JSON qui circulent

      
n8n est un outil d'automatisation « low-code » : on assemble visuellement des nœuds, et on descend dans le code (JavaScript, Python, expressions) seulement quand c'est utile.

    


    

      

        

        
Trigger

        
Chaque workflow démarre par un déclencheur : Webhook, Schedule (cron), un événement d'app (nouvel email, nouvelle ligne…), un formulaire ou un chat.

      

      

        

        
Nœuds

        
Chaque nœud fait une chose : appeler une API, transformer des données (Edit Fields, Code), router (If, Switch), fusionner (Merge), boucler.

      

      

        

        
Items JSON

        
Entre deux nœuds circule une liste d'items. Chaque item est un objet json. Un nœud s'exécute une fois par item — 10 leads en entrée, 10 appels en sortie.

      

      

        

        
Expressions

        
Tout paramètre peut être dynamique : {{ $json.email }} lit l'item courant, {{ $('Webhook').item.json.body }} lit un nœud précédent.

      

      

        

        
Agents IA

        
Le nœud AI Agent branche un modèle (Claude, etc.), une mémoire et des outils. L'agent décide lui-même quels outils appeler pour accomplir la tâche.

      

      

        

        
Exécutions

        
Chaque run est journalisé avec les données de chaque nœud. On rejoue, on débogue, on « épingle » des données de test. Un workflow d'erreur prévient en cas d'échec.

      

    


    

      

        Le point clé pour le dev d'interfaces
        
Un nœud Webhook transforme n'importe quel workflow en endpoint d'API

        
    
          
  • Une URL par workflow. /webhook-test/… pendant que vous testez dans l'éditeur, /webhook/… une fois le workflow activé.
    • 
          
  • Vous choisissez la réponse. Répondre tout de suite, à la fin du dernier nœud, ou via un nœud Respond to Webhook qui renvoie exactement le JSON attendu par le front.
    • 
          
  • Sécurisable. Authentification Header / Basic / JWT, origines CORS autorisées, méthode HTTP imposée.
    •

      Architecture
      
Le front parle HTTP, n8n fait le travail

      
L'interface générée par Claude Code ne contient aucune logique métier sensible ni clé d'API tierce. Elle envoie une requête au webhook, le scénario n8n orchestre les services, puis renvoie un JSON propre.

    


    

      

        Interface
        

          généré par Claude Code
          
Formulaire / App web

          
HTML, React, Next.js… Valide la saisie, affiche le chargement et le résultat.

        

      

      

        Transport
        

          HTTPS · JSON
          
POST /webhook/lead

          
En-tête X-API-Key, corps JSON. Idéalement via une route serveur (proxy) pour ne pas exposer la clé.

        

      

      

        Orchestration
        

          workflow n8n
          
Scénario

          
Validation → Agent IA → Condition → Actions. Journalisé à chaque exécution.

        

      

      

        Services
        

          APIs tierces
          
CRM, IA, Slack, BDD

          
Les identifiants restent dans le coffre de n8n (Credentials), jamais dans le front.

      Bonnes pratiques
      
Ce qui sépare une démo d'un outil en production

    

    

      
Indispensable
Authentifier le webhook
Activez Header Auth sur le nœud Webhook. Sans ça, n'importe qui connaissant l'URL peut déclencher le scénario.

      
Indispensable
Garder les secrets côté serveur
Le navigateur appelle votre route /api/lead, qui ajoute la clé et appelle n8n. La clé n'apparaît jamais dans le JavaScript public.

      
Indispensable
Valider deux fois
Côté front pour l'expérience, côté n8n (If ou Code) pour la sécurité. Répondez 400 avec un message clair si l'entrée est invalide.

      
Recommandé
Un format de réponse unique
Toujours { ok, data, error } via Respond to Webhook. Le front n'a qu'un seul cas à gérer.

      
Recommandé
Traitements longs en asynchrone
Au-delà de quelques secondes, répondez 202 avec un identifiant, puis laissez le front interroger un second webhook de statut.

      
Recommandé
Workflow d'erreur
Branchez un Error Trigger qui notifie Slack ou email : vous savez qu'un scénario a échoué avant l'utilisateur.

    

  







  

    

      FAQ
      
Questions fréquentes

    

    

      

        Pourquoi mettre la logique dans n8n plutôt que dans le code du front ?
        
Parce que la logique métier change souvent et implique beaucoup d'intégrations. Dans n8n, elle est visible, modifiable sans redéployer l'interface, et chaque exécution est tracée. Le front reste simple : il envoie et affiche.

      

      

        Claude Code peut-il créer le workflow n8n lui-même ?
        
Oui, si vous connectez le serveur MCP de votre instance n8n à Claude Code. Il peut alors rechercher des nœuds, créer et valider un workflow, l'exécuter en test et lire le résultat — puis écrire l'interface qui l'appelle, dans la même session.

      

      

        Quelle différence entre l'URL de test et l'URL de production ?
        
/webhook-test/… ne répond que lorsque vous cliquez sur « Listen for test event » dans l'éditeur, et affiche les données en direct. /webhook/… fonctionne en continu, une fois le workflow activé (publié).

      

      

        Et si le scénario prend 30 secondes ou plus ?
        
Ne faites pas attendre le navigateur. Répondez immédiatement avec un identifiant de tâche, stockez l'état (Data Table n8n, base de données), et exposez un second webhook GET /status?id=… que l'interface interroge.

      

      

        n8n cloud ou auto-hébergé ?
        
Les deux fonctionnent de la même façon pour les webhooks. L'auto-hébergement (Docker) donne le contrôle total des données ; le cloud évite la maintenance. Seule l'URL de base change dans vos variables d'environnement.
